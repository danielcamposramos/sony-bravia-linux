## What is open

### The next leg — SDL, X11, Wayland stereo signalling

First measurement phase is complete and its conclusion changes the framing: **on this host
the kernel drops all stereo modes before userspace can see them.** Full evidence record in
`tools/stereo-kms-probe/README.md`. Short version, all verified in the linux 7.0 source tree
plus a read-only live probe:

- The EDID declares SBS-half + top-and-bottom on a 7-VIC mask and frame packing on VICs
  5, 20, 34, 60, 62. `drm_edid.c`'s `add_alternate_cea_modes` creates 3D-flagged alternates
  unconditionally.
- Probe-time validation prunes them with `MODE_NO_STEREO` unless `connector->stereo_allowed`,
  which is a per-driver choice: i915 = true (intel_hdmi.c:3097), nouveau = true for G92+
  HDMI/DP (nouveau_connector.c:1420), vc4 = 1 (vc4_hdmi.c:589), **amdgpu DC = explicitly false
  (amdgpu_dm.c:8975)**, nvidia-drm = never set (615.71.09 DRM source has no stereo handling
  at all, so it defaults false).
- Probe results on the KDL-46HX855 (amdgpu): 22 modes without caps, 22 with STEREO_3D,
  30 with ASPECT_RATIO, 30 with both — zero stereo in every pass. The earlier sysfs(30) vs
  userspace(22) discrepancy was aspect-ratio duplicate filtering
  (`drm_mode_expose_to_userspace`), not stereo.
- Daniel's fact stands and now has its mechanism: NVIDIA X11 enabled 3D on this TV because
  the X server bypasses DRM connector mode lists; the KMS arm of the same driver cannot.

Consequences: compositors/SDL are off the hook on this host — there is no stereo mode to
request. The upstream target list is now kernel-first: amdgpu DC (explicit deny) and
nvidia-drm (absent flag), with i915/vc4 as working counter-examples. Pending one-command
verifications are in the README.

### The unlock attempt Daniel approved late 2026-09-20 — **SUCCEEDED**

Status: **PASS, [proven]** on the KDL-46HX855, run 7 at 19:26-19:28 UTC-3. Full record:
`tools/stereo-modeset/README.md` + `run7-pass-2026-09-20.log`. The Sony switched itself
into 3D on the SBS-half modeset (no remote button) and Daniel perceived the disparity
pattern in depth. Probe numbers: stock 22 modes / 0 stereo with the cap set → patched
51 modes / **29 stereo**. Both patches held.

amdgpu DC turns out to have stereo bones: `dc_stream.view_format` with SBS/TaB scaler
translation, a stereo plane-address flip in the hwseq layer, an `hfvsif` info-packet path
that is never populated, and `drm_hdmi_vendor_infoframe_from_display_mode()` already being
called in `fill_stream_properties_from_drm_display_mode()` with the 3D fields discarded.
Two patches applied to the local linux-source 7.0 tree (fudged to SUBLEVEL=10 for vermagic):

1. `amdgpu_dm_connector_init_helper`: `stereo_allowed = true`.
2. `fill_stream_properties_from_drm_display_mode` HDMI branch: pack the vendor infoframe
   and attach it as `stream->hfvsif_infopacket` when the mode carries 3D flags.
   `timing_3d_format` deliberately stays NONE (it drives DC's stereo plane-address flip,
   wrong for a userspace-composed SBS buffer).

`tools/stereo-modeset/` (stereo-modeset.c + run-3d-test.sh) is the bare-VT smoke test:
sets the caps, picks the 1080p60 SBS-half mode, draws three boxes at disparities
-32/0/+32. Pass = the TV switches into 3D by itself. Run detached via systemd-run so the
desktop can be stopped from inside itself. Windows 11 on the **same AMD iGPU HDMI port and
cable** offers a 3D mode in display properties and auto-switches this TV [proven — Daniel,
2026-09-20], closing the hardware question: gap is purely amdgpu's Linux driver. Run 1 hit
a trailing-space vermagic precheck (fixed), run 2 hit `modprobe -r amdgpu: in use` (fixed:
terminate the user session and unbind fbcon first), run 3 found `/tmp` wiped at boot (fixed:
build tree now at /K3D/temp/k317). Run 4 died at `insmod: Unknown symbol in module`:
`modprobe -r` had taken the unused 16-module dependency chain down with it and bare insmod
resolves nothing — and the script marched on driverless, leaving an alive-but-pictureless
box (keyboard/disk worked, SysRq/Ctrl+Alt+Del would have recovered it; Daniel hard-reset).
Fixed: preload dep chain from the stock module description, abort+full-restore on insmod
failure, final card0 sanity check swaps back to stock before sddm restarts, SysRq armed for
the run. The **patch itself has still never executed** — runs 1-4 all failed before it.

### nouveau verification on the RTX 3060 — CLOSED, [proven] end to end

Run 4 (20:26-20:28 UTC-3): SBS-half 1920x1080@60 modeset on stock nouveau made the
KDL-46HX855 switch itself into 3D; Daniel confirmed the depth test visually.
Record: `tools/stereo-modeset/run4-nouveau-modeset-pass-2026-09-20.log` (probe
51/29 stereo + 33 mode lines + full clean restore: nvidia stack, daemons, sddm,
all 5 docker containers back). Nouveau ships BOTH halves — exposure and VSIF
emission — matching its source claims (nouveau_connector.c, dispnv50/disp.c).
Restore worked fully this run: nouveau removed cleanly once the session's fds
were dead, guard removed, nvidia_drm re-bound card1.

Ecosystem scoreboard after today (grep over the full 7.0 tree): exactly THREE
mainline drivers ever set `stereo_allowed`: i915 (intel_hdmi.c:3097, with VSIF
packing at :820-838), nouveau, vc4 (vc4_hdmi.c). Our patch makes amdgpu DC the
fourth. `drm_bridge_connector.c:809` carries a literal upstream
`TODO: Handle doublescan_allowed and stereo_allowed` — the generic bridge
connector modern ARM HDMI pipelines sit behind. Every other HDMI-capable driver
(rockchip/meson/imx/rcar/sun4i/mtk/msm/tegra/exynos/omap/tda998x class) leaves
the flag unset, so their 3D-capable sinks get pruned exactly like amdgpu did.
A one-line allow + per-driver VSIF-in-commit audit is the campaignable follow-up;
i915 is the living reference implementation.
