## What is open

### The next leg — SDL, X11, Wayland stereo signalling

First measurement phase is complete and its conclusion changes the framing: **on this host
the kernel drops all stereo modes before userspace can see them.** Full evidence record in
`tools/stereo-kms-probe/README.md`. Short version, all verified in the linux 7.0 source tree
plus a read-only live probe:

- The EDID declares SBS-half + top-and-bottom on a 7-VIC mask and frame packing on VICs
  5, 20, 34, 60, 62. `drm_edid.c`'s `add_alternate_cea_modes` creates 3D-flagged alternates
  unconditionally.
- Probe-time validation prunes them with `MODE_NO_STEREO` unless `connector->stereo_allowed`,
  which is a per-driver choice: i915 = true (intel_hdmi.c:3097), nouveau = true for G92+
  HDMI/DP (nouveau_connector.c:1420), vc4 = 1 (vc4_hdmi.c:589), **amdgpu DC = explicitly false
  (amdgpu_dm.c:8975)**, nvidia-drm = never set (615.71.09 DRM source has no stereo handling
  at all, so it defaults false).
- Probe results on the KDL-46HX855 (amdgpu): 22 modes without caps, 22 with STEREO_3D,
  30 with ASPECT_RATIO, 30 with both — zero stereo in every pass. The earlier sysfs(30) vs
  userspace(22) discrepancy was aspect-ratio duplicate filtering
  (`drm_mode_expose_to_userspace`), not stereo.
- Daniel's fact stands and now has its mechanism: NVIDIA X11 enabled 3D on this TV because
  the X server bypasses DRM connector mode lists; the KMS arm of the same driver cannot.

Consequences: compositors/SDL are off the hook on this host — there is no stereo mode to
request. The upstream target list is now kernel-first: amdgpu DC (explicit deny) and
nvidia-drm (absent flag), with i915/vc4 as working counter-examples. Pending one-command
verifications are in the README.

### Frame packing and the Steam Frame question — implementation staged

`tools/stereo-modeset/stereo-modeset` now accepts `sbs`, `tab` and `fp`.
For 1080p24 frame packing it allocates the DRM-required 1920x2205 scanout:
one 1080-line eye, the mode's 45-line vertical blanking interval, then the
second 1080-line eye. Both detached harnesses pass the selector through.
The first run should use stock nouveau as the known-positive timing path:

`sudo systemd-run --unit=nouveau-3d-test --collect sh /K3D/GitHub/sony-bravia-linux/tools/stereo-modeset/run-nouveau-test.sh fp`

[proven, source audit] DRM represents the mode as logical 1920x1080@24 and
`drm_mode_set_crtcinfo(..., CRTC_STEREO_DOUBLE)` doubles the clock and link
vertical timing. Nouveau calls that helper and explicitly accepts an input
height of `vdisplay + vtotal`; i915 also calls the helper. amdgpu's DRM-to-DC
translation currently fixes `timing_3d_format` to NONE, so the minimal patch
that proved SBS/TaB signalling does not yet program full frame-packing wire
timing. DC nevertheless contains frame-packing enums, bandwidth treatment,
OPP/OTG stereo programming, view formats and packet builders. The gap is an
unwired Linux translation path, not evidence that AMD display hardware is
incapable.

[proven, source audit] wiz3D already performs the other half of Daniel's
proposal: its Direct3D output reads separate left and right backbuffers and
packs them into SBS or TaB output rectangles. A Linux compositor/output
backend can do the same with OpenXR eye images. SBS/TaB need a packing shader
plus a stereo DRM mode; full frame packing additionally needs the driver
timing transformation above. Current gamescope exposes no such TV-3D output
target. Full analysis and the Android correction are recorded in
`docs/dual-surface-hdmi-3d.md`.

Physical topology correction from Daniel: AMD and NVIDIA were connected to
two HDMI inputs of the same BRAVIA. Switching inputs during the test showed
both paths in 3D; AMD was black and NVIDIA showed the lower portion of its
retained frame. The AMD process committed only card0/HDMI-A-1, so the NVIDIA
state came from its own preceding FP path rather than a cross-GPU DRM commit.
This proves two independent links can signal 3D to the sink and qualifies the
future topology: AMD→one of EX725/HX855 and NVIDIA→the other. Two physical TVs
at once remain [qualified] until run.

Future tests now default to one-link isolation. The AMD harness removes only
`nvidia_drm` (CUDA/UVM and containers stay live), the modesetter blanks other
CRTCs on card0, and `nvidia_drm` is restored before SDDM. Do not interpret the
dual-link observation as a reason to skip this isolation while fixing AMD's
black FP scanout.

The black scanout now has a source-level candidate cause. DRM gives the
primary plane 2205 lines through `drm_mode_get_hv_timing()`, but amdgpu creates
its DC stream from the unadjusted 1080-line mode because its CRTC mode-fixup is
a no-op and the atomic path does not consume `adjusted_mode`. The experimental
module `/K3D/temp/k317/amdgpu-fp-experimental.ko` expands only the local FP
stream timing and its stream rectangle to 2205/2250 lines at 148.5 MHz while
leaving DC stereo addressing disabled. It compiled against 7.0.10+deb14-amd64
and is [inferred, not hardware-tested]. The AMD harness selects it only for
`fp`; SBS/TaB use the preserved known-good module.

Dual-TV performance requirement from Daniel: negotiate one common mode for
the EX725 and HX855 so the stereo eyes are rendered once and packed once. The
VSIF is cheap per connector. Different output packings would require separate
final compositor passes; separate GPUs may also need DMA-BUF import or a copy,
but neither should imply rerendering the game scene for each display.

The activation side is broader than rendering. H.264/H.265
`frame_packing_arrangement` SEI, Matroska StereoMode, MPO metadata, player
hints and OpenXR eye surfaces should all produce one normalized stereo-intent
descriptor. A compositor/display policy consumes it, intersects it with EDID,
packs once for compatible sinks, commits the HDMI mode+VSIF, and restores 2D
when the track or session ends. SEI state must persist between keyframes rather
than disappear on the following decoded frame. This turns the Android VLC
watcher into a prototype of the policy while removing the need for one watcher
per player once intent is propagated end to end.

Daniel's Windows recollection supplies the compositor shape: HDMI 3D is a
global output mode, while one logical desktop window may supply paired left
and right buffers. The compositor places each buffer into the same window
rectangle on its corresponding eye canvas; mono windows and UI are duplicated
to both eyes at screen depth, then both completed canvases are packed once.
This is the direct bridge from Steam Frame/OpenXR per-eye composition to a flat
TV output. Linux still needs a surface-pairing contract plus the HDMI packing
backend.
